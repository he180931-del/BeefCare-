theo từng luồng chức năng.

Mỗi thành viên nhận một nhóm chức năng, tự kiểm tra code cùng agent, viết test và sửa phần chưa đúng. Làm xong luồng nào thì bàn giao API của luồng đó cho FE nối. Không bắt buộc review chéo.

Luôn theo thứ tự này

Use case (UC): người dùng làm gì, theo thứ tự nào. Business rule (BR): điều kiện phải tuân theo. SCR: trường và thông báo trên màn hình. ERD: dữ liệu liên kết thế nào. Swagger: API hiện có. Dùng yêu cầu trong tài liệu để kiểm code, không lấy code hiện tại làm đáp án.

0/7 bước tự đánh dấu

Checklist lưu riêng trên trình duyệt này, dành cho một gói UC. Đánh dấu bước không tự đánh dấu API hoàn tất; kết quả bàn giao nằm ở bảng API.

Đường đi của code: nhánh riêng → tự test và sửa → gộp phần đã xong vào main → chạy bản chung → FE nối. Xem lệnh Git và xử lý conflict ↓

1
Chọn việc

Chọn một luồng chức năng để làm đến nơi đến chốn.

Cần làm gì?

Chọn UC thuộc phần mình phụ trách. Ghi rõ ai được dùng, cần dữ liệu gì trước, và những API nào tham gia. Chọn phạm vi nhỏ nhưng sử dụng được từ đầu đến cuối.

Đọc / kiểm chứng ở đâu?
SRS · danh sách & mô tả UCTab phân công 4 người

Ví dụ: tạo phiếu nhập → ghi sổ → xem lại phiếu và bò đã nhập. Ghi rõ thanh toán/sửa/hủy có nằm trong lần này hay chưa.

Phải thu được →Một danh sách: UC cần làm, API liên quan, vai trò và dữ liệu cần chuẩn bị.

Sang bước tiếp khi: Khi đã biết rõ làm phần nào, kết thúc ở kết quả nào và cần API của ai.

Phối hợp: Nếu cần dữ liệu/API của người BE khác, báo người đó. Hỏi FE phần nào họ sắp nối.

Git ở bước này: Từ main mới nhất, tạo nhánh theo gói UC, ví dụ be/herd-entry-review. Mỗi checkout nên làm một việc; kiểm file đang sửa trước khi chuyển nhánh.

2
Biết thế nào là đúng

Đọc yêu cầu và ghi kết quả đúng phải là gì.

Cần làm gì?

Cùng agent viết các trường hợp cần kiểm. Mỗi trường hợp có: dữ liệu ban đầu → thao tác → kết quả phải nhận được. Ghi cả trường hợp thành công và bị từ chối, kèm mã UC/BR làm căn cứ.

Đọc / kiểm chứng ở đâu?
UC · điều kiện trước/sau, luồng chính, nhánh lỗiQuyền · trạng thái · GBR / BR-DSCR · trường / thông báoERD · quyết định Dxx

Ví dụ: Technician không được ghi phiếu; không dùng dữ liệu trại khác; một dòng lỗi thì không nhập nửa đàn.

Phải thu được →Bảng điều kiện cần đúng và nguồn yêu cầu. Ví dụ: “Owner post phiếu 2 dòng → có đúng 2 bò và đúng số chỗ chuồng”.

Sang bước tiếp khi: Mỗi trường hợp quan trọng đã có kết quả mong đợi và nguồn để đối chiếu.

Phối hợp: Chỉ hỏi chủ dự án khi tài liệu và quyết định đã có không giải được mâu thuẫn.

3
Kiểm phần đang có

Đọc code, chạy test cũ và ghi phần sai hoặc thiếu.

Cần làm gì?

Đi theo đường API → dữ liệu đầu vào → hàm xử lý → truy vấn/lưu DB. Đọc các hàm được gọi bên trong. Sau đó chạy test liên quan đang có, trước khi sửa.

Đọc / kiểm chứng ở đâu?
Bảng API · input / output / codeDanh sách cần đúng ở bước 2

Mỗi vấn đề phải phân biệt: code sai, test cũ sai yêu cầu, chưa có test, API thiếu trường, tài liệu chưa rõ, hoặc máy chưa chạy được.

Phải thu được →Kết quả chạy ban đầu và danh sách việc phải sửa/bổ sung, gắn với đúng API/hàm.

Sang bước tiếp khi: Đã biết phần nào có bằng chứng đúng, phần nào sai và phần nào chưa được kiểm.

Phối hợp: Có thể gửi FE bản mô tả API dự thảo để dựng trước; chưa báo API đã hoàn tất.

Git ở bước này: Ghi commit gốc vào kết quả chạy. Các test/cách gọi API phải khớp phiên bản code này, không chỉ dựa vào log cũ.

4
Viết test và sửa code

Viết test → sửa code → chạy lại test.

Cần làm gì?
  1. Viết/bổ sung test cho điều kiện ở bước 2 còn thiếu bằng chứng.
  2. Chạy test. Nếu đang sửa bug, test phải thể hiện được bug đó.
  3. Sửa code chưa đúng ở hàm/API/DB liên quan. Code đã đúng thì chỉ bổ sung test cần thiết.
  4. Chạy lại test vừa viết và test cũ bị ảnh hưởng. Còn lỗi thì tiếp tục vòng này.
Đọc / kiểm chứng ở đâu?
UC / BR / SCR ở bước 2Code và vấn đề ở bước 3

Đây là bước sửa chức năng. Không chỉ viết test rồi ghi nhận lỗi để đó. Nếu test cũ sai yêu cầu thì sửa test có căn cứ; không đổi kết quả mong đợi để che lỗi code.

Viết loại test nào?Dùng khi cần kiểm
Unit · một rule/hàmCông thức, nhánh điều kiện, giá trị biên. So với BR và ví dụ tính tay.
Integration · nhiều phần + DBQuery, lưu nhiều bảng, ràng buộc, rollback, lịch sử. So với UC/ERD/state.
API/HTTP · request thậtInput/output, mã lỗi, quyền/trại, session/CSRF, key/version. So với SCR/quyền/UC.

Chọn tầng phù hợp, tái dùng test đang đúng. Một test API có DB cũng là integration; không cần viết test trùng chỉ để đủ ba loại.

Phải thu được →Code đã sửa trong phạm vi nhận; test kiểm được hành vi đó; ghi tên test và kết quả chạy.

Sang bước tiếp khi: Các điều kiện quan trọng đã được kiểm, lỗi chặn đã sửa; phần chưa kiểm được ghi rõ.

Phối hợp: Báo người giữ phần dùng chung trước khi sửa quyền, trạng thái, DB hoặc API ảnh hưởng tới họ.

Git ở bước này: Commit theo phần sửa có nghĩa, push nhánh riêng để lưu/chia sẻ tiến độ. API còn “Đang kiểm/Còn vướng”; push nhánh chưa phải bàn giao.

5
Kiểm cả luồng

Gọi các API theo thứ tự và xem kết quả trong DB.

Cần làm gì?

Chạy backend với PostgreSQL. Gọi API theo đúng luồng người dùng: tạo → xác nhận/ghi sổ → đọc lại → sửa/hủy nếu có trong phạm vi. Kiểm dữ liệu liên quan sau từng bước.

Đọc / kiểm chứng ở đâu?
UC · toàn luồng và kết quả cuốiBR · giao dịch / trạng thái / quyềnERD · dữ liệu liên quan

Kiểm thêm khi áp dụng: sai quyền/trại, gửi lặp, bản ghi bị người khác sửa, lỗi giữa chừng, lịch sử. Với tiền/tồn/đầu con, so với số tự tính.

Phải thu được →Bằng chứng cả luồng đúng: API trả gì, DB còn gì, số liệu có khớp không. Ghi commit, DB và cách chạy lại.

Sang bước tiếp khi: Nếu sai: quay bước 4 để sửa, rồi chạy lại bước 5. Chỉ sang bước 6 khi luồng trong phạm vi đã đúng.

Phối hợp: Cùng BE liên quan kiểm các luồng như đẻ → nhập bê, bệnh → xuất đàn, thay đàn → cho ăn/báo cáo.

Git ở bước này: Trước khi chốt, lấy main mới vào nhánh của mình, giải quyết conflict rồi chạy lại phần bị ảnh hưởng và luồng UC. Nếu main lại đổi phần liên quan thì kiểm lại trước khi gộp.

6
Chốt và bàn giao API

Đưa code đã kiểm lên bản chung, cập nhật bảng API.

Cần làm gì?

Tự kiểm lại phần sửa cùng agent. Đưa code lên theo quy tắc nhánh của nhóm, chạy lại phần bị ảnh hưởng trên bản chung. Khi API đổi trường/route, cập nhật OpenAPI tương ứng.

Đọc / kiểm chứng ở đâu?
Bảng API · phần kết quả tự kiểmKết quả bước 4 & 5

Ghi: người phụ trách, commit, UC/BR đã chốt, điều kiện trường, test đã chạy, môi trường và giới hạn. Chỉ chọn “Đã xong” khi không còn lỗi chặn trong phạm vi.

Phải thu được →API vào tab “Đã kiểm chứng & bàn giao”. FE nhận URL + commit + mô tả input/output/lỗi + dữ liệu test + thứ tự gọi.

Sang bước tiếp khi: FE dùng được đúng bản BE/contract đã kiểm; nhóm đã nhận file HTML hoặc JSON cập nhật.

Phối hợp: Người tổng hợp gộp bản cập nhật của 4 BE. Không cần một vòng duyệt chéo bắt buộc.

Git ở bước này: Một đầu mối gộp lần lượt gói đã kiểm vào main; kiểm bản tích hợp rồi push. Cập nhật bảng API với commit/URL/contract thực tế. Không chờ cả 4 người xong và không gộp phần dở chỉ vì FE cần nối.

7
FE nối và phản hồi

FE làm màn hình, BE hỗ trợ xử lý lỗi kết nối.

Cần làm gì?

FE tự dựng màn và test giao diện với API thật. BE cung cấp dữ liệu test và hỗ trợ khi request lỗi hoặc kết quả khác tài liệu.

Đọc / kiểm chứng ở đâu?
API đã bàn giao ở bước 6UC / SCR · luồng và dữ liệu hiển thị

Lỗi BE: mở lại “Còn vướng” → bước 4 sửa → bước 5 kiểm luồng → bước 6 cập nhật. Lỗi UI/mapping: FE sửa; BE giải thích contract khi cần.

Phải thu được →FE xác nhận luồng nối được; vấn đề còn lại có người xử lý. Bắt đầu gói UC tiếp theo.

Sang bước tiếp khi: Có kết quả kiểm tích hợp thực tế; không coi API có trên Swagger là FE đã dùng được.

Phối hợp: BE và FE phụ trách cùng chức năng. Không cần đợi mọi feature của backend xong.

Git ở bước này: FE làm trên nhánh UI riêng, cập nhật từ main và dùng backend bản chung đã bàn giao. FE không cần tự gộp từng nhánh BE. Production giữ cho bản cuối.

Ba điểm dễ hiểu nhầm trong repo: mvn test mặc định bỏ lớp *IT; @ServiceIntegrationTest dùng H2; compose đang PostgreSQL16 nhưng testcontainer khai báo 18.4. Ghi suite/DB thực chạy, thống nhất phiên bản mục tiêu; không suy ra đã kiểm PostgreSQL từ H2 hoặc tổng số test xanh.
Git theo từng bước: nhánh riêng → main → FE

Bản chung để tích hợp là main. Mỗi thành viên làm ở nhánh riêng theo gói chức năng, push để lưu/chia sẻ tiến độ. Push nhánh riêng chưa có nghĩa API đã được bàn giao.

  1. Tạo nhánh gói UC từ main mới nhất, ví dụ be/herd-entry-review.
  2. Tự kiểm cùng agent theo bước 1–5. Trong lúc làm có thể push nhánh riêng; API vẫn ở trạng thái Đang kiểm/Còn vướng.
  3. Khi gói đủ điều kiện bước 6, cập nhật từ main, giải quyết conflict và kiểm lại phần bị ảnh hưởng. Người điều phối gộp lần lượt vào main, tránh gộp đồng thời migration/contract khác nhau. Đây không phải yêu cầu review chéo.
  4. Chạy bản tích hợp, cập nhật OpenAPI và bảng API với đúng commit/URL, rồi bàn giao FE.
  5. FE làm nhánh UI của mình từ main, gọi backend bản chung đã bàn giao. FE không cần tự chọn và gộp từng nhánh BE để lấy API.

Nếu cần thử gói chưa hoàn tất, BE/FE thống nhất một nhánh/môi trường thử tạm và ghi rõ chưa bàn giao. Nhánh production chỉ nhận bản sản phẩm cuối đã nghiệm thu.

Lệnh tham khảo — thành viên BE

Chạy tại gốc repo, ví dụ gói nhập đàn. Đổi tên nhánh và đường dẫn theo phần mình. Trước khi chuyển/merge nhánh, giữ lại các thay đổi đang làm bằng commit phù hợp; không reset hoặc bỏ file để làm sạch.

# 1. Tạo nhánh mới từ main đã cập nhật (khi checkout đã sạch).
git status
git switch main
git pull --ff-only origin main
git switch -c be/herd-entry-review

# 2. Sau mỗi phần sửa + test: chọn đúng file, commit và push nhánh riêng.
git diff
git add <các-file-thực-sự-liên-quan>
git commit -m "test(herd-entry): verify posting and rollback"
git push -u origin be/herd-entry-review

# 3. Trước bàn giao: vẫn ở nhánh feature, đưa main mới vào.
git fetch origin
git merge origin/main
# Nếu conflict: xử lý theo nội dung, kiểm lại diff, hoàn tất merge.
# Sau đó chạy lại test bị ảnh hưởng + luồng UC, rồi push nhánh feature.

Không dùng force-push để xử lý việc main đã tiến lên. Với conflict DTO/migration/contract, phối hợp người giữ phần đó; không chọn nguyên “ours/theirs” để bỏ qua thay đổi của người khác. Ghi phiên bản sau merge vào bằng chứng.

Lệnh tham khảo — người tổng hợp bản chung

# Khi gói đủ điều kiện và nhánh feature đã push.
git switch main
git pull --ff-only origin main
git merge --no-ff origin/be/herd-entry-review
# Chạy test liên quan + kiểm bản tích hợp, kiểm contract và cập nhật bảng API.
# Chỉ push khi bản tích hợp đủ điều kiện bàn giao.
git push origin main

Nếu kiểm bản tích hợp lỗi: sửa ở đúng scope và kiểm lại trước khi push; chưa công bố API đã xong. Nếu đã push và phát hiện lỗi chặn: mở lại trạng thái API, báo FE bị ảnh hưởng, làm bản sửa trên nhánh riêng; chỉ rollback/revert khi đã đánh giá tác động migration/dữ liệu. Khi gộp xong, lấy main mới để tạo nhánh cho gói tiếp theo.

Chia sẻ bảng API giữa 4 người

Mỗi người cập nhật các API thuộc scope mình, xuất JSON. Người tổng hợp nhập các JSON vào bản HTML chung rồi xuất HTML cập nhật và commit file đó. Các API trùng scope cần một người chịu trách nhiệm; không merge mù hai khối JSON nhúng. API đổi contract phải được kiểm lại trước khi đánh dấu hoàn tất.

python docs/tools/generate_api_catalog.py
